# samograph web — UI audit (condensed, 2026-09-04)

Condensed findings from two read-only audit passes over `apps/web` and prod
(`https://samograph.samo.team`): a desktop pass (commits `bb166cf` #256 → `98465c3` #274, 1200px
viewport) and a mobile + other-pages follow-up pass (`main` @ `53dcf30`, 390×844 and 1024×900
viewports, via a same-origin iframe). These findings are what [`DESIGN-MODEL.md`](./DESIGN-MODEL.md)
answers and what [`PLAN.md`](./PLAN.md) schedules. Screenshots referenced below were captured
during the audits and are not checked into the repo; descriptions are given in place of the image
files.

---

## Desktop findings

### 1. The `<select>` was completely unstyled
No `appearance: none`, no chevron of ours, no width limit. Measured a 656×37px box holding the
4-letter word "blip", with the browser's default chevron glyph ~640px from the value it belonged
to. *(Screenshot: 4× zoom on the Chat-chime select showing the floating chevron; the top of the
Settings page showing the oversized select boxes.)* — **Fixed: PR 1 (#278).**

### 2. Five different control heights
`.samograph-btn` 36px, `input`/`textarea` 40px (implicit), `select` 37px,
`.samograph-google-signin` 40px, theme-switcher options 44px, in-panel buttons 44px,
`.samograph-btn--sm` 28px. On `/dashboard` the hero form is `align-items: end` with a 40px input
beside a 36px button — they could never align. *(Screenshot: the dashboard hero row showing the
input/button height mismatch.)* — **In review: PR 2 (#279).**

### 3. Settings content 200px out of alignment with the app nav
Nav inner box used `max-width: var(--width-app)` (1120px); the prose page wrapper used
`max-width: var(--width-prose)` (720px), applied to `<main>` itself rather than to its content —
so the two boxes centred independently. Measured at 1200px viewport: nav starts at x=40, settings
content at x=240; a 150px version of the same bug measured again at 1024px on the mobile-audit
pass (brand x=32 vs H1 x=182). *(Screenshot: Settings top, brand wordmark and H1 visibly offset.)*

### 4. Buttons stretch to full width on Settings
`.samograph-signin` is `display: grid`; the calendar connection card reuses that class, so every
child (including the button pair) stretches to a grid item. Measured: Reconnect/Disconnect
rendered 656px wide, stacked. *(Screenshot: Settings Integrations section, full-width stacked
buttons with an orphaned alert.)*

### 5. Flat type hierarchy
Every section heading (`h2`) was 16px/600 with no rule, no eyebrow, no surface distinguishing it
from body text — "Add samograph to a call", "Upcoming meetings", "Past calls" and "Danger zone"
read as four visually identical peers. *(Screenshot: dashboard, light mode.)*

### 6. Dark mode: illegible disabled buttons, near-invisible hairlines
`[disabled]` was `opacity: .5` only, so a disabled primary button (ink background) becomes
grey-on-grey. `--line` on `--ground` measured ~1.15:1 contrast — list-row separators effectively
vanish in dark mode. *(Screenshot: dashboard dark mode, "Add to call" button illegible.)*

### 7. Two design languages in one product
The marketing landing page used a monospace font throughout, full-bleed 56px gutters, a 68px nav,
and a `.samograph-button` class at 44px/`.74rem`. The app used Inter, a centred 1120px layout,
32px gutter, 64px nav, and a same-but-different `.samograph-btn` class at 36px/`.8125rem` — two
class names one letter apart with different geometry. *(Screenshots: landing page vs. dashboard,
side by side.)*

### 8. Three loading idioms, the good one used once
A proper skeleton component existed but was wired to only one Suspense fallback; two other
surfaces rendered bare `<p role="status">Loading …</p>` sentences instead.

### 9. Alerts read as colored boxes, and the class does two jobs
The entire alert message (not just an accent) was rendered in the tone color, with no icon and no
title — reading as decoration rather than a sentence. The same class doubled as both an inline
savebar status and a full-width page banner. *(Screenshot: Settings Integrations, an orphaned
error box between two section rules.)*

### 10. A raw URL used as page title and list-row title
The call-view H1 was the literal meeting URL at 28px/700; dashboard list rows used the same raw
mono URL as their primary line, with one row displaying a 70-character Zoom link. The list-row
grid also left roughly 700px of empty space between the title and its CTA on desktop.
*(Screenshots: call view showing the URL-as-heading; dashboard row.)*

### Honourable mentions (desktop)
- `role="switch"` on auto-record rendered as a plain checkbox.
- Two stacked focus signals on fields (global outline + a border-color change).
- `.samograph-btn` inherited its border from a bare `button` rule rather than declaring one —
  `<a class="samograph-btn">` had no border at all.
- Four different border radii live in one viewport (6 / 8 / 10 / 999px).
- The same `z-index: 1000` was reused for both the skip-link and the modal.
- The sticky settings savebar was narrower than the viewport with page background visible on
  both sides and no shadow lifting it off the content.
- Three unrelated breakpoint values (`59.99rem`, `48rem`, `40rem`) with `/settings` having no
  responsive rules of its own.
- `textarea` forced a monospace font globally instead of scoping it to the one field that needs
  it.

## Mobile + other-pages findings

Method: prod walked at 390×844 (mobile) and 1024×900 (desktop) inside a same-origin iframe so
real CSS media queries resolved. `/auth` could not be walked live (a signed-in visitor is
redirected before it renders) and was audited statically instead; a signed-out pass is still
owed.

**Headline: there is no horizontal overflow anywhere — the breakage is proportion, not overflow.**
Every page's `scrollWidth === innerWidth` with zero elements wider than the viewport. The failure
mode is that the desktop layout gets *squeezed* rather than *reflowed*: fixed-width grid columns
keep their shape on a much narrower content box, headers wrap into multiple stacked rows, and
text shrinks below readable sizes to keep fitting. The fix is reflow rules, not overflow patches
— this drove the responsive model in `DESIGN-MODEL.md` §5.

### `/calls/<id>` — the worst page on mobile
This is the page the product exists for, and it was the least usable one on a phone:
- The transcript grid kept its four desktop columns at 390px width, just shrunk — the utterance
  column (the actual product content) measured 113.9px wide, about 33% of the content box and
  roughly 14 characters at 11.52px font size. Line numbers, a repeated date, and a truncated
  speaker name consumed the other 56%.
- Eighteen elements measured at 11.52px, seven at 11.2px, and one — a security-relevant "Share
  link · owner controlled" label — at 10.56px, the smallest text in the product.
- The sticky status header alone consumed 19% of the viewport height (161px), and combined with
  the 129px app nav and a two-line URL-as-H1, the first line of transcript sat ~470px down an
  844px screen.
- The H1 was the raw meeting URL, wrapping across two 28px lines and consuming ~90px, while the
  same URL was already repeated in the panel header directly below it.
- Several footer/header controls were well under the 44px touch target minimum (a 20px-tall back
  link, 36px share/delete buttons).
- The transcript's own internal scroll region (`max-height: min(62vh, 680px)`) created a second,
  competing scroll area nested inside the page scroller with no visual seam.
*(Screenshot: call view top at mobile width, showing the oversized nav and two-line URL heading.)*

### `/dashboard`
- Nav consumed 129px before any page content appeared.
- List rows stacked correctly but each was three lines of low-value content (a raw mono URL, a
  status chip, a "View transcript" link) with no title, date, or duration — and on desktop the
  same row wasted an 811px gap between the URL and its CTA.
- Control heights still mismatched (40px input vs. 36px button), more visible once both went full
  width on mobile and sat stacked with a visible 4px difference.
- A destructive "Permanently delete account" action was sized at 36px tall on a touch surface.
- **A privacy defect the original top-10 pass missed:** at 1024px width, a Zoom meeting URL
  rendered in full including its `?pwd=` query string — a join secret displayed verbatim in the
  UI. At 390px this happened to get truncated, but only by accident of layout, not by design.
*(Screenshots: dashboard hero and rows at mobile width; the desktop row showing the printed Zoom
password and the CTA gap.)*

### `/settings`
The best of the four pages on mobile, largely because the select fix (PR 1) had already landed.
- The select control was correctly sized at 390px — the field-max token already exceeded the
  content box width, so it read as full-width, which is the right mobile behavior.
- Section dividers (six identical heavy rules stacked down a narrow column) read as "divider
  soup" with nothing distinguishing which rule opens which section.
- The same full-width stacked button bug from the desktop pass was present on mobile too.
- The sticky savebar floated over the last 62px of content with no shadow and page background
  visible on both sides; at 1024px it literally overlapped the bottom border of the last select
  field on the page.
- The disabled "Save settings" button was grey-on-grey — visible in light mode too, not just
  dark, confirming the disabled-state bug is `opacity`-only rather than theme-specific.
*(Screenshots: Settings sections at mobile width; the desktop savebar overlapping the last
select.)*

### App shell / nav — no mobile nav exists
The only responsive rule was a `flex-wrap: wrap` patch. Measured at 390px, the nav resolved to
129px tall total (15% of an 844px screen) on every page, with the account email wrapping across
three lines mid-word, a 154px-wide theme switcher (the widest interactive element on the page for
a preference nobody changes mid-session) with 10.88px labels, and every nav link under the 44px
touch-target minimum. There was no hamburger, no drawer, no overflow menu, and no current-page
indicator. *(Screenshot: 1.7× zoom on the mobile nav showing the wrapped email.)*

### `/` landing
- The mobile breakpoint hid both the product wordmark and the nav call-to-action, leaving an
  unlabelled avatar and an oversized theme switcher — the product's name did not appear on its
  own landing page at mobile width.
- Footer separator glyphs rendered visually on the line above their associated links at every
  viewport width, due to a baseline mismatch between an inline glyph and flex-wrapped link text —
  a plain desktop bug the original top-10 pass missed. *(Screenshot: footer nav at 1024px showing
  the misplaced separators.)*
- Measured text sizes as low as 9.73px (a strapline), with several more controls between 11–13px.
- A dead CSS rule (`min-width: 780px` on a component no longer in the DOM) was found still
  present — a latent overflow risk if that component is ever reintroduced.

### `/auth` (static audit only)
Three different control geometries stacked in one 480px form: a 40px Google sign-in button
(intentionally fixed by Google's branding requirements), a 40px magic-link input, and a 36px
submit button at a different border radius. A signed-out live pass is still owed.

### Cross-cutting mobile findings
- No `viewport-fit=cover` and no safe-area-inset handling anywhere — the sticky savebar, the
  jump-to-live pill, and the panel footer all sit under the iPhone home indicator on notched
  devices.
- Three untokenised breakpoint values, all expressed as `max-width` patches on a desktop base;
  no mobile-first (`min-width`) rule existed anywhere.
- `/settings` had no responsive rules at all prior to this pass.
- Type sizes below 14px were found scattered across the app as raw literals (not tokens) at ten
  distinct values from 9.73px to 13.6px.
- Touch-target counts under 44px: 9 on `/dashboard`, 7 on `/settings`, 7 on `/calls/<id>`, 1 on
  `/`. Only the theme switcher options, the in-panel transcript buttons, and the landing
  brand/footer links already cleared 44px.
